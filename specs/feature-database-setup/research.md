# Research: Database Migration to PostgreSQL

All Technical Context unknowns are resolved below. No `NEEDS CLARIFICATION` items remain.

## R1. Database driver

- **Decision**: `psycopg` 3 (`psycopg[binary]`), raw SQL, `dict_row` row factory so existing `row["col"]` access keeps working.
- **Rationale**: Keeps the "no ORM, parameterised SQL" rule. Supports `bytea` as `bytes` and server-side transactions. Pin `psycopg[binary]==3.3.6`: checked on 2026-10-26 that PyPI publishes `psycopg_binary-3.3.6-cp314-cp314-manylinux2014_x86_64` for Python 3.14, so no system libpq is needed. On platforms without a binary wheel, fall back to `psycopg[c]` or plain `psycopg` plus a system libpq.
- **Alternatives**: `psycopg2` (older API, no benefit); SQLAlchemy/asyncpg (ORM or async, contradict the constitution's simplicity principle).

## R2. Placeholders and SQL dialect

- **Decision**: Replace `?` with `%s` in every query (about 25 call sites). Replace SQLite-only constructs:
  - `COLLATE NOCASE` ordering → `ORDER BY lower(description)`.
  - Case-insensitive username uniqueness → unique index on `lower(username)`; login lookup uses `lower(username) = lower(%s)`.
  - `substr(date, 1, 7)` → keep as-is (works in PostgreSQL on `text`).
  - `ON CONFLICT ... DO UPDATE SET limit_cents = excluded.limit_cents` → unchanged (valid in PostgreSQL).
  - `sqlite3.IntegrityError` → `psycopg.errors.UniqueViolation` in `auth.register`.
- **Rationale**: Smallest change that preserves behaviour (FR-009). A query-translation shim would hide bugs.
- **Alternatives**: `citext` extension (needs extension privileges on the operator's server); a placeholder-rewriting wrapper (fragile).

## R3. Column types

- **Decision**: `date` stays `text` holding `YYYY-MM-DD`; `amount_cents` and `limit_cents` are `bigint`; ids are `bigint GENERATED BY DEFAULT AS IDENTITY`; `photo` is `bytea`. CHECK constraints are kept.
- **Rationale**: ISO text dates sort and filter correctly and keep `substr(date,1,7)` month grouping and all filter code unchanged. Changing to `date` is a separate improvement.
- **Alternatives**: native `date` type (touches filters, charts, exports); `integer` cents (limits headroom for no benefit).

## R4. Schema versioning and concurrent start-up

- **Decision**: A `schema_version` table with one row replaces `PRAGMA user_version`. `init_db()` takes `pg_advisory_xact_lock` inside a transaction before reading the version and applying pending migrations, so several Gunicorn workers or servers starting together apply each migration exactly once. Each migration still runs in its own transaction (PostgreSQL DDL is transactional, so no table rebuilds are needed).
- **Rationale**: `app.py` calls `init_db()` at import, so every worker runs it.
- **Alternatives**: running migrations from a separate release step only (changes the deployment model); no lock (race on first start).

## R5. Migration chain for PostgreSQL

- **Decision**: New chain whose `_migrate_v1` creates the current schema (equivalent to SQLite v4) using a frozen category list `_PG_V1_CATEGORIES`. Later changes append `_migrate_v2…`.
- **Rationale**: SQLite v1-v4 contain SQLite-only logic (see Complexity Tracking). The SQLite chain stays in git history and in the README as the legacy path.
- **Alternatives**: port all four steps (no value on a new database).

## R6. Data migration command

- **Decision**: Flask CLI group in `expense_tracker/sqlite_import.py`:
  - `migrate --source PATH` opens the SQLite file read-only (`mode=ro`), requires `user_version == 4` (otherwise refuses with instructions to upgrade using the previous release), requires an empty target, then copies `users`, `expenses`, `monthly_limits`, `profiles` in one PostgreSQL transaction preserving ids and bytes, and finally resets each identity sequence with `setval` to the highest copied id.
  - `verify --source PATH` compares row counts per table, per-user expense sums in cents, a checksum of photos, and the password hashes, and exits non-zero on any difference.
- **Rationale**: One transaction gives all-or-nothing (FR-005). Read-only open guarantees the source is unmodified. Copying hashes keeps logins working (FR-004).
- **Alternatives**: `pgloader` (extra tool, hard to guarantee cent-exactness checks); dump/restore SQL (needs dialect rewriting).

## R7. Offline cutover and maintenance page

- **Decision**: Add `MAINTENANCE_MODE` configuration. When true, a `before_request` hook returns `maintenance.html` with HTTP 503 and `Retry-After` for every route except static files, and `init_db()` is skipped so the app does not touch the database. The runbook sets it, restarts the app, migrates, verifies, then clears it.
- **CLI interaction**: `flask --app app ...` imports `app.py`, which builds the app. With maintenance mode on, start-up skips `init_db()`, so the `migrate` command calls `init_db()` itself against the target before copying.
- **Rationale**: Satisfies FR-018 without depending on proxy configuration the project does not own. The hook is registered ahead of CSRF/body-size handling so it works for POSTs too.
- **Alternatives**: proxy-only maintenance page (works, but not testable in this repo); stopping the app (users see an error page).

## R8. Rollback and verification window

- **Decision**: The runbook defines the window as the time between switching the app to PostgreSQL (still in maintenance mode) and clearing `MAINTENANCE_MODE`. Rollback means: keep maintenance mode on, redeploy the previous release tag, point it at the untouched SQLite file. The SQLite file is kept read-only and unmodified until the window closes and is archived afterwards.
- **Smoke check inside the window**: the public instance stays in maintenance mode. The operator starts a second instance with maintenance mode off, bound to `127.0.0.1` on a spare port that the proxy does not route, and checks login, the list page and an export there. That instance is stopped before the window closes.
- **Rationale**: Matches the clarified decision (no reverse migration).
- **Alternatives**: reverse migration tool (rejected in clarification).

## R9. Local development and tests

- **Decision**: `compose.yaml` starts `postgres` with a named volume and health check. `POSTGRES_DB` creates `penny_dev`; a script mounted into `/docker-entrypoint-initdb.d` (`docker/initdb/01-create-test-db.sql`) creates `penny_test` on the first start of an empty volume. Tests use `TEST_DATABASE_URL` (default points at the compose test database) and create a throwaway schema per test, set through the connection's `search_path` via `DATABASE_SCHEMA`, dropped at teardown. The `app` fixture passes both through `create_app` overrides.
- **Rationale**: Isolation like the old per-test `tmp_path` database, without creating a database per test (slow).
- **Alternatives**: database per test (slow); transaction rollback per test (breaks code that commits).

## R10. Concurrency semantics

- **Decision**: Keep one transaction per request (`db.commit()` as today). Every write is a single statement (INSERT, UPDATE, DELETE, upsert), so there are no read-modify-write races. Concurrent edits to the same expense are last-write-wins. Session cookies are signed client-side, so sessions already work across servers if `SECRET_KEY` is identical.
- **Rationale**: Meets FR-011 and User Story 3 without optimistic locking, which the spec does not require.
- **Alternatives**: optimistic locking with a version column (new behaviour, out of scope).

## R11. Connection handling

- **Decision**: One connection per request stored in `g`, closed on teardown, as today. No pool.
- **Rationale**: At under 100 users with a few Gunicorn workers the connection count is small. A pool can be added later without API changes.
- **Alternatives**: `psycopg_pool` (extra moving part; revisit if connection limits are hit).

## R12. Secrets and logging

- **Decision**: `DATABASE_URL` is read from the environment only. Error handling and logging report the host and database name but never the URL or password; connection errors are caught in `get_db()` and re-raised with a redacted message.
- **Rationale**: FR-012 and SC-007.

## Constitution re-check after design

The design complies with constitution 2.0.0, which was amended before implementation to cover
the three deviations recorded in plan.md. No new violations were introduced by the design in
